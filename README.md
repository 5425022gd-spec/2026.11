# 天启七年 · AI 驱动文字游戏（引擎原型 v0.3）

引擎：状态 / 时间 / 省份图 / 公式 / 动作 / 事件剧本 / 邸报 + 网页界面（零依赖，
仅标准库）。LLM 层：内阁条陈（AI 提案 → 引擎校验）+ 邸报润色。未配置 key 时自动
进入确定性 mock 模式，整条管线无网络可演示。

## 运行

**一键启动（唯一入口）：**

```
双击 start.bat          # 或命令行 ./start.ps1
```

启动脚本自动完成：检测 Python → 显示 AI 模式 → live 模式下先校验连接 → 启动网页
服务器 → 打开浏览器（http://127.0.0.1:8010）。

```
./start.ps1 -Diag        # 只跑 AI 连接诊断
./start.ps1 -NoDiag      # 跳过启动时自动诊断
./start.ps1 -NoBrowser   # 不自动打开浏览器
python diag.py           # 独立诊断脚本
```

游戏命令（网页输入框）：

| 命令 | 说明 |
|---|---|
| 数字 / 省id | 查看省份详情（含地方数据：核心/人口/阶级/镇军/天气/工程），如 `1` 或 `shaanxi` |
| `j` | 推进时间：`j` / `j 3` / `j 2m 5d 3h`（月/日/时；跨日触发凌晨批处理：不重要事件/次要事件/月度总结） |
| `w` | 润色本月邸报（文案层示例） |
| `mem` | 查看当日章奏列表 |
| `view <id>` | 阅读章奏正文 |
| `read <id>` | 已阅（归档） |
| `reply <id> <回折>` | 撰写回折 |
| `new` | 重开新局 |
| `s` / `l` | 存盘 / 读盘（`save.json`） |
| `q` | 退出 |

## LLM 配置（可选）

不配置也能玩（mock 模式）。接入真实 AI，编辑 **`config/llm.json`**：

```json
{
  "base_url": "https://api.deepseek.com/v1",
  "api_key": "sk-你的key",
  "model": "deepseek-chat",
  "mock": null
}
```

- `mock: null` = 自动（无 api_key 则 mock）；`true` 强制 mock。
- 配置优先级：**文件 > 环境变量**（`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` / `LLM_MOCK`）> 内置默认。
- 请求头/请求体模板见 **`config/request_template.md`**（可直接复制到 Postman / 网关）。
- 游戏内输入 **`diag`** 校验 AI 连接：配置摘要 → HTTP/聊天请求 → 工具（function calling）请求，逐项报告是否正常。

## 官职（engine/positions.py + data/positions_seed.json）

**一张表，六列，全项目只有这一个官职来源**：

| 列 | 说明 |
|---|---|
| 职位名称 | 内阁首辅 / 延安府知府 / 总兵官（宁远） |
| 人名 | 空 = 缺员。缺员会显示成「缺员」，由**月度铨选**补授（见下），不是读界面时生成 |
| 职位类型 | 京官 / 文职 / 武职。**写在数据里**，不按职位名关键字猜 |
| 职位分类 | 前端的分栏键：京官填部门名（吏部、司礼监），文职/武职填省名（辽东、湖广） |
| 开始时间 | 到任月 |
| 截止时间 | 空 = 在任或关键人物（不参与到期替换）；有值 = 该随机官员到点换人 |

- 计数：**京官 232（45 个部门编制）/ 文职 288 / 武职 50，合计 570**；开局 7 个缺员槽。
- 三个前端出口全部读这张表：部门「现任管理层」（京官·本部门）、吏部「文册档案」（文职·按省）、
  兵部「武官人事」（武职·按省，辽东单列）。
- **缺员怎么补**：月度结算时由 `positions.fill_vacancies(now)` 补授，**缺几个补几个，不设上限**，
  补的人带开始时间、进变化池（`【铨选】…缺员，补授 X`）、
  进推进日志与月度总结。**读界面永远不写表**——原来 229 个京官就是「打开界面发现缺员 →
  随机生成一个人」灌出来的，那才是错的：补官是游戏进程，不是读数据的副作用。
- 上游只有五个写入口：开局建库、超控增删职位、铨选调任、月度到期替换（`positions.replace_expired`）、
  月度铨选补官（`positions.fill_vacancies`）。
- 重建库：`python tools/rebuild_positions.py`（从种子与部门编制重新生成 570 行并重建表）。
- 口径断言在 `tests/test_positions_unified.py`：计数、类型合法性、分类归属、唯一性、日期顺序、
  读界面不写表、铨选补官带开始时间、三个出口行数与表一致。
- **已删除**：`officials.title` 自由文本、`is_military_title()` 关键字判武职、
  `list_by_province(exclude_central/exclude_military)` 布尔开关、`data/positions.json` 第二份编制、
  读界面时的缺员自动 `spawn_official`。

## 地方数据（world/provinces.json → local）

按玩家预案，每省 `local` 只存原始设定，派生值由 `engine/localdata.py` 计算：

| 字段 | 说明 |
|---|---|
| `core` | 核心情况：核心（数值最好）/ 宣称（部分数值）/ 占领（仅军事占领） |
| `classes` | 地方阶级（宗室/士绅/商人/农民/百工/百役/流民），各阶级存 `pop/attitude/output/tax_rate/support`（态度一个字段统民心与忠诚） |
| `infra` | 基建程度 0-100 |
| `army` | 军队（机动部队，留空）：`training` + `equipment{类型:{in_service 在役, authorized 编制}}` |
| `projects` | 地方工程（要塞/城池/工程/港埠…） |
| `carrying` | 可承载人口（当前科技与经济形式下的自然承载力） |
| `terrain` | 地形（接口，后续细化到地块） |
| `weather` | 天气（引擎季度计划生成：雨/雪按当月温度判定；大雨/台风/大旱/大涝/热浪/寒潮；地震删除留接口） |

镇军（地方治安军队或武装力量）**不在地方数据里**：军队数据只有一份，全在 `world/armies.json`
（见 `engine/armies.py`）——`count` 人数 / `pay_rate` 发饷比例 / `arrears_wan` 欠饷，
军饷需求由人数乘常数现算（`PAY_PER_MAN = 1.5` 两/人·月，维护 `MAINT_PER_MAN = 0.35`）。

派生值（不存档）：**地方人口** = 各阶级人口总和；人口基础自然率为每月出生 +0.3%、死亡 -0.2%（顺序复合后净增约 +0.0994%，实际还受人口修正、饥荒、流民转化和阶级迁移影响）；**税收**由户部税目按各自税基与时点结算。

### 建筑（工程，`local.projects`）

- 一个工程六个属性：名称 / 修正（`buff`）/ 范围（`scope`）/ 建筑类型（`kind`）/ 状态（`status`）/ 造价（`cost`）。
- 类型只有五类：国家建筑 / 军事建筑 / 工程建筑 / 灾害建筑 / 矿场。
  **军事建筑不挂数值修正**（故意如此），只在 `buff.desc` 写介绍。
- **年维护费不是存档字段**：按「造价 × 1%」现算，月维护＝年维护 ÷ 12，未完工的不计
  （`engine/depts_works.py`）。界面上那列是派生值，改它没有用。
- **损毁是数字不是二值状态**：`pj["damage"]` 取 0~1，`status` 仍是运营中／未完工。
  一切效果按 **1 − 损毁程度** 折算（`engine/projects.py`），产能、白银、黄金、减灾都一样。
  大黄汛的损毁程度由 `damage_degree` 这条修正算，超控写 `工程损毁程度 <省> <工程> <百分比>`。
- **灾害效果写成词条**，不再是一句散文：`buff.disaster[kind]` 与 `buff.disaster_chance[kind]`，
  kind 与词条表里的 `kind` 一一对应。例：
  - 海宁海塘：`disaster: {flood_minor: -0.70, flood_major: -0.70}`
    → 界面上写「小涝导致的产能损失-70%，大涝导致的产能损失-70%」；
  - 灵州黄河石堤：`disaster: {yellow_flood: -0.20, yellow_flood_major: -0.20}` +
    `disaster_chance: {yellow_flood: -0.20}`
    → 「黄汛导致的产能损失-20%，大黄汛导致的产能损失-20%，黄汛发生概率-20%」。
- 工程减免**走修正系统的同一个收集口**（`_from_projects`），按唯一公式参与计算，
  不是先乘一个系数的旁路；词条自己声明作用面（涝类本省、黄汛类全国）。

## 修正（engine/modifier_registry.py + world/modifiers.json）

- **一个修正 = 名称 + 效果列表 + 介绍**，是个独立对象。`from` 只说明它挂在哪个界面，
  **不决定它影响谁**——「党争工具」一条修正同时打中央腐败 +20% 与地区腐败 +2%。
- **唯一公式**（全站只此一处实现）：

      值 = 基础值 × (1 + Σ乘法修正) + Σ加法修正

- **数据源**：静态修正在 `world/modifiers.json`（6 条）；运行时来源（部门政纪/现行法律、超控部门修正、
  科技效果、宗教、教育加成、朝廷赏罚、地方独立修正、天时）统一由 `contributions()` 的 provider 登记处收集，
  子系统**不自己算值**。
- **界面只有一种形态**：四列——修正项目 / 修正范围 / 修正效果 / 介绍（`modTable4`，全文只此一处表头）；
  工程表是八列的另一形态（多出建筑类型 / 状态 / 造价 / 年维护费），两者不混。
- 每个被影响的系统都要在自己的面板里列出贡献明细（`value()` 返回 `breakdown`）。

## 科技树（world/techs.json + engine/tech.py）

- 每条科技写自己的**直接前置**（`prereqs`），后置由前置反查得出，不存第二份关系表；
  节点坐标 `(x, y)` 的零点＝`png/keji.png` 左上角，直接就是图里该科技名的中心位置
  （新科技用 `tools/keji_texts.py` 从 PSD 文字层读坐标，图上没有的名目不写进来）。
  排布照图，前后置照设计，两者不混。
- 两棵树：理论科学 / 科学技术（`world/techs.json` 的 `trees`，界面上部两个页签切换）。
- 运行状态随存档：`state.tech_points` 科技点（开局 10 点，见 world/provinces.json 的 `tech_points`）、
  `state.tech_unlocked` 已解锁科技。**科研点来源＝任务 / 成就 / 主线结案**（见下），
  唯一的发点口是 `engine/tasks.grant_tech_points`；每条科技的解锁消耗写在 `world/techs.json` 的
  `cost`（当前每条 1 点），解锁规则与按钮文案只在 `engine/tech.py` 的 `unlock_state()` / `unlock_text()` 一处判定，
  接口 `POST /api/tech/unlock`。
- **科技效果**：`world/tech_effects.json`（一条科技一组 `target/value/desc`）＋`engine/tech_effects.py`。
  登记的 target 与消费点：`financial_rate`→`state.financial_rate`（基础值＋科技＋部门修正）、
  `capacity`→`modifiers.build_local_modifier_index` 的中央产能项、`carrying_pct`→`depts_libu.calc_local_carrying`、
  `central_corruption`/`prestige`/`population_birth`/`population_death`/`edu_growth`/`higher_edu_growth` 各自的既有消费点。
  解锁即生效（`tech.unlock` 里重算一次），读档也会按「基础值＋效果」重算，不会与存档里的旧派生值分叉。
  科技界面的「效果」由结构化效果现渲染，`techs.json` 的 `effect` 字段不再另写一份。
- **任务**：`world/tasks.json`＋`engine/tasks.py`，数值达标的一次性任务，达成发科技点；
  指标只在 `engine/tasks.py` 的 `METRICS` 登记一处。界面：科技界面右侧「任务」。
- **成就**：`world/achievements.json`＋`engine/achievements.py`，廷议的衍生系统。
  开会时把核查数据（科技是否解锁、地块是否控制、数值是否达标）交给 AI，由 AI 判定结束条件，
  判定通过由引擎发科技点。首版只有「教育改革」。
- 界面：主界面左上角是**科技入口**（占住左上角，中上数据栏随之挤窄，入口上直接显示科技点）；
  进科技界面即**直接显示理论科学树**，科技树本身就是背景，浮在更上一层的按钮条给出
  科技点（左上）、理论科学与科学技术两个树切换按钮（上部）、任务与成就（右侧）。
  树页面按坐标摆节点：**同一条线内的前后置画箭头，从数学线或物理线跨到别的线来的画连线**
  （这类边若其上游已有别的节点带着同一条前置，就不再画）。箭头端点按名牌的真实矩形求交、
  箭头三角按方向用代码算出（不用 SVG marker），所以横斜一致、缩放也跟着走；点科技后它自己的
  箭头与连线转不透明。右侧滑出介绍面板（前置 / 后置 / 文字介绍 / 效果 + 底部解锁按钮，
  高约占界面三分之二、垂直居中），背景是随平移缩放走的方格纸，树很大时进入倍率不低于 0.5 倍。
  每条科技的"线"写在数据里（`line`：数学/物理/化学/生物/地理/工学/医学/科学）。
- 读口只有一个：`GET /api/tech` → `engine.tech.tech_view(state)`；主界面入口的点数走 `/api/state` 的 `tech_points`。

## 天气系统（玩家方案 v2，world/climate.json + engine/weather.py）

- 静态气候：每省 `月度温度表`（全月唯一温度）+ `季度降水量表`（春/夏/秋/冬累计 mm），
  数据在 `world/climate.json`（按东亚气候资料撰写，可调）。
- 季度调度（每季初）：骰小降水占比 30%~40% → 余 60%~70% 为大降水占用量；
  降雨日随机 20~35 天，小降水按单日上下限分配；大降水事件
  （春夏型 monsoon 春4~6/夏6~8 随机选省；秋冬型冷锋 秋4~6/冬6~8 自北向南 3 批，
  批次间推迟 1~2 天）每省一次 = 该省季量 × 大降水占比，覆盖省配额恰好用完、单省不超 100%。
- 雨雪判定：当月温度 ≤0℃ 为雪，>0℃ 为雨。
- 极端天气（整季偏移，不写数值影响）：大旱/大涝每年随机一季（旱涝互斥）；
  热浪仅夏季、寒潮仅冬季（概率触发，寒暑不错季）。
- 台风：仅秋季，沿海省（含东番，东番权重×2）1~3 个，每次≤1 省，降水独立于大降水占用量。
- 地震：已删除（留接口）。

## 设计纪律（对话讨论的落地）

- 事件由 AI/模板驱动：不重要事件（模板库）+ 次要事件（zhixian 提示词）+ 事件树（unzhixian 推演），引擎只分配 ID 与时间戳。
- 时间是状态变量，归引擎所有；叙事永远从账本读时间。
- 数值由玩家直接设定（地方数据/阶级），派生值（人口/税收/民变）由引擎按公式计算，不双写存档。
- 存档 = 一个 JSON；调试 = 直接改 JSON。

### v0.5.5（修正模型：唯一公式 + 数据化；建筑特殊处理）
- **唯一公式**（`engine/modifier_registry.apply_formula`，全站只此一处实现）：

      值 = 基础值 × (1 + Σ乘法修正) + Σ加法修正

  样例：基础值 1，乘法 +1% +2% +3%，加法 +1 +2 +3 → 1 × 1.06 + 6 = **7.06**。
  原来 `depts_libu` 三处、`depts_rites` 威望、`economy` 的产能与需求各写了一遍同款算式，
  现已全部改为调用这一个函数（测试会扫引擎，发现第二处同款算式就报错）。
- **修正是一个独立对象**：名称 + 效果列表 + 介绍。效果各自打一个系统（`target`），

  中央腐败（+20%）与地区腐败（+2%）。
